Case study A

The chip that hijacked its own bus

Bulk EEPROM writes kept failing mid-sequence on a shared I²C bus. Nine plausible causes were tested and killed before the real one surfaced.

System
ES005 pendant — STM32 + CH334F USB hub sharing an I²C bus with a 24LC02 EEPROM
My role
Firmware; sole software engineer on the programme
Tools
Bit-banged I²C, USB-CDC command shell, logic analyser, SWD

Context

The hub reads its descriptor config — VID/PID, strings, serial — from the EEPROM at boot, sharing STM32 pins PA2/PA3. To provision a unit, the STM32 pulls the hub's RESET low to take the bus, then bit-bangs I²C to write config, driven by a USB-CDC command interface (CHECK / READ / WRITE / BLANK / FLASH). Single-byte operations worked perfectly from day one. Bulk operations — a 256-byte blank, a ~33-byte full flash — kept failing partway through.

Elimination, by direct test rather than assumption

  1. Bad EEPROM cellFailure address moved run to run.
  2. Bad data patternBlanking to all-0xFF failed too.
  3. Page-boundary bugFailures landed on unaligned addresses.
  4. Write-cycle raceACK polling changed nothing.
  5. Clock too fast for the busSlowing the clock made it worse.
  6. Address-specific faultPivotal test: starting the blank at 0x80 still failed at the same operation count, not the same address.
  7. Write/read couplingIsolating write-only still failed.
  8. Repeated-start protocol bugSingle reads use the same repeated-start and always work. A real protocol bug fails on operation #1, not #39.
  9. Something outside the transaction is taking the busTwo clues pointed here: a slower clock failed sooner — the opposite of a bus-margin problem — and a longer idle delay before writing also failed sooner. The clock was running from the moment RESET went low, whether or not real work was happening. The failure was time-bound, not signal-bound.

The decisive experiment

Before each page write, release the bus to high-Z and sniff SDA and SCL directly.

  • Healthy — bus idle11
  • At failure — held00

Both lines snapped to zero and stayed there — actively driven low, not floating.

Root cause

The behaviour is consistent with the hub repurposing its I²C-capable pins as LED-driver outputs after boot: roughly 1–1.5 s after the RESET falling edge, both shared lines are driven low regardless of bus activity, and holding RESET low doesn't clear it — which points to a level-latched internal state change rather than anything happening on the bus. This is the best explanation the evidence supports; I haven't confirmed the pin multiplexing against the vendor datasheet.

Fix

Pulse RESET before each small write chunk to re-arm a fresh time budget — one 8-byte page per pulse, about 32 resets for a full 256-byte blank, verified clean throughout. The permanent fix, scheduled for the next board spin, is a load switch gating the hub's power pin so it's fully off during provisioning: no powered chip, nothing to latch.

Why it matters

Nine confident, plausible-sounding theories died against evidence before the real mechanism surfaced. The discriminating test — reading the bus state directly — should have run first, not ninth. That changed how I sequence diagnostics: find the test that splits the hypothesis space before running the ones that only confirm a favourite theory.

Transferable

Cost of the wrong order: eight test cycles. Cost of the right one: a single capture. Ordering tests by how much they eliminate, not by how likely they are to be right, is the whole lesson.

Case study B

The clock that lied

A fielded clinical device kept losing time. The kernel said the clock was fine.

System
CM4-based oximeter, deployed for clinical investigation
My role
Root cause, firmware fix, RCA and test SOP
Stack
Linux, rtc-ds1307 kernel driver, DS3231 RTC

Context

Intermittent timestamp failures on units already in the field — the worst possible place for a bug that undermines the clinical data record.

Investigation

Traced the rtc-ds1307 driver path against the DS3231 datasheet. The Oscillator Stop Flag — the exact signal designed to warn that the clock is untrustworthy — was being masked.

Root cause

A dead backup battery. The RTC lost oscillation on power-down, but the driver path never surfaced the flag to userspace, so the system reported a valid clock while holding invalid time.

Fix and prevention

Firmware fix shipped to fielded units, plus a written root-cause analysis and a test SOP, so the failure mode is explicitly checked rather than remembered.

Why it matters

A silent failure in a safety-relevant path. The work wasn't the fix — it was making an invisible failure state visible, and then making the check part of process so it can't quietly go missing again.

Pattern

A component reporting health is not the same as a component being healthy. The interesting question is always which layer dropped the warning.

Case study C

Real-time vitals from a raw camera stream

10-bit Bayer frames in, SpO₂ and pulse rate out — concurrently, and without touching disk.

System
Class A medical device software, Linux SBC, USB camera
Standards
IEC 62304, ISO 13485, ISO 14971
My role
Owned the software transition from research code to regulated device software

Approach

Custom parsing of the 10-bit pre-Bayer format with a bespoke RGB conversion that fits inside the frame budget, with no measurable increase in end-to-end latency against the unconverted path. Linux IPC — shared memory and semaphores with double buffering — so acquisition and analysis run concurrently without contention and without a disk I/O bottleneck. The mutex and semaphore design was reviewed explicitly for race conditions rather than assumed correct.

Regulatory dimension

This is the programme where I owned the IEC 62304 documentation set: Software Development Plan, SOPs, dFMEA, configuration management, problem resolution, and requirements traceability through to verification. Architecture documented in UML/SysML with sequence diagrams; risk controls traced from the dFMEA into specific code paths. Alongside it, requirements engineering across a cross-functional team, a custom I²C driver for an SSD1309 OLED surfacing live vitals and patient warnings, and device configuration for EMC testing.

Engineering judgement — the stack that had to change

The R&D precursor to this system was an Electron/React GUI over an async Python backend — the right call for a fast, polished demo on a PC, with the backend built to be portable. When the target moved to a constrained SBC, the backend ported cleanly. The Electron frontend didn't, and had to be rebuilt in PyQt.

The fix worked. The honest lesson is upstream: on an R&D project with that many unknowns, the deployment envelope should have been probed before committing to a heavy frontend framework, not after. It changed how I approach stack decisions — decouple the tested core from the UI early, keep the choice reversible, and ask about the hardware target before the demo target.

Case study D

From silicon to shipped: owning the Windows application

One engineer, four layers — custom board firmware, USB protocol, a C#/.NET desktop app, an Android app. This is the desktop half.

Product
The Gamer's EarSwitch — in-ear control device, shown at CES 2026
My role
Sole software engineer: requirements, architecture, implementation, test, packaging, release, docs, support diagnostics
Stack
C# / .NET, WPF, MVVM, USB CDC

Context

The device lets a user trigger a game action with an ear movement — built for streamers and, more importantly, for players with limited hand mobility. The Windows application is the primary experience: it takes camera frames, detects the ear click, calibrates to the individual user, and injects the mapped input into whatever game is running.

Architecture

  • Layered — device transport (USB CDC serial) → signal and detection → view models → XAML views.
  • Seams for testing — the transport layer sits behind an interface, so detection logic can be exercised against recorded frames with no pendant attached. Dependency injection for composition, so swapping in a mock device is a one-line change. The seam exists and is used; coverage is partial rather than complete.
  • Threading discipline — frame acquisition and processing off the UI thread, marshalled back via the dispatcher, with backpressure so a slow UI can never stall acquisition.
  • Input injection into the foreground game, with the mapping configurable per user.

A deliberate UX call

A persistent status card rather than toast notifications. A toast on every ear click would be unusable mid-game — the user needs to glance at state, not be interrupted by it. Small decision, but it's the kind that only gets made by someone who understands both the signal and the person using it.

Release engineering

Versioned, installable builds produced through the pipeline rather than from a developer machine; a written release checklist so a release is a repeatable procedure and not a memory exercise; and structured logging written for support rather than for the author — when a user reports that it stopped detecting, the log should say which layer failed.

Why it matters

The interesting engineering in a consumer hardware product isn't only in the firmware. The application is where the hardware's ambiguity becomes a user-facing promise — your ear click will register, every time, fast enough to matter — and keeping that promise is an architecture problem, a threading problem, and a release-discipline problem at the same time.

Scope

No separate application team to hand any layer to. Every decision from the USB byte format to the installer was one person's, which is uncomfortable and clarifying in roughly equal measure.

Case study E

The app that had to prove it was assistive

An app that presses buttons in other apps looks exactly like the automation Google Play bans. Getting it through review meant proving it was the opposite — while running the whole signal pipeline on-device.

Product
Android version of the Gamer's EarSwitch
My role
Took it from R&D prototype through architecture, hardware interface, on-device processing, and Play policy preparation
Stack
Kotlin / Java, Accessibility Services, foreground services, USB host / BLE

The structural problem

On Android, injecting input into other apps means the Accessibility Services API. That API is under heavy Play scrutiny for good reason — it's the same mechanism used by malware, click-farms, and automation tooling — so policy requires that an app using it exists to help users with disabilities, declares that use explicitly, and discloses it prominently. The Gamer's EarSwitch genuinely is an assistive input device; that's the origin of the product. But "genuinely assistive" isn't a technical property a reviewer can read off a binary. It has to be argued, evidenced, and made legible in the listing, the in-app disclosure, and the declaration.

Hardware interface on a platform that doesn't want you talking to hardware

  • A device link with a connection state machine that survives detach and reattach, permission revocation, and the user unplugging mid-session.
  • A foreground service with a persistent notification, so the pipeline keeps running when the app isn't in front — and so it satisfies Android's background execution limits rather than being silently killed.
  • Doze, battery optimisation, and OEM-specific process killing handled explicitly rather than discovered in the field.

On-device signal processing

Ear-click detection runs entirely on the phone. That's a latency requirement first — a click has to register fast enough to be usable in a game, and a round trip to a server is not an option — and it also made the Data Safety declaration straightforward: nothing to declare, because nothing leaves the phone. Per-user calibration handles the fact that every ear, every fit, and every pendant seating is slightly different.

Cross-platform parity — the hard part nobody sees

The same detection logic behaved more sensitively on Android than on the PC. A fishbone and 5-whys under time pressure traced it to an optimisation in my own pipeline that had raised the noise floor. Fixed, bringing the Android detection output back in line with the PC pipeline across the test set — which matters because a user shouldn't effectively get a different device depending on what they plug it into.

Preparing for review

  • Accessibility-services declaration and permissions justification, with the assistive use case evidenced rather than asserted.
  • Prominent in-app disclosure explaining what the service does and why it needs the permission.
  • A Data Safety declaration backed by the on-device architecture — the privacy claim is true because of a design decision, not a promise.
  • Privacy policy, store listing, and staged testing tracks.

Why it matters

Building it right was necessary and not sufficient. Getting it in front of users meant making a case, to a review process designed to assume the worst about this exact API, that the app is what it says it is. What made that case winnable was an architectural choice made months earlier to process everything on-device.

Transferable

Compliance work is usually decided long before the form is filled in. The privacy answer was already true; all that was left was showing why.

How I build and maintain

Process, sized to the risk

The clinical programme has IEC 62304 forcing discipline on it. The commercial programme has nothing forcing anything — which is exactly how an early-stage consumer product ends up an unmaintainable prototype that ships anyway.

I set the process for the Gamer's EarSwitch software deliberately: borrowing the parts of regulated practice that earn their keep, and dropping the parts that only exist to satisfy an auditor.

  • Source control and review

    A defined branching strategy and pull-request review across firmware, desktop, and Android, so no change reaches a release build without a second look.

  • CI/CD on GitHub Actions

    Automated build pipelines for each layer, producing versioned artifacts. A broken build is visible immediately rather than at release time.

  • Versioning and release

    A written release checklist, so a release is a repeatable procedure rather than a memory exercise.

  • Documentation that survives me

    Architecture and design documentation where it earns its place, interface and protocol specifications for the USB CDC command set, decision records for the choices that would otherwise get re-litigated by whoever inherits the code, test plans, and user-facing docs.

  • Traceability, proportionate

    I carried over the habits that earn their keep from the regulated side — written interface specs, recorded design decisions, a defined path from issue report to verified fix — without the full traceability apparatus, which this risk profile doesn't justify. Knowing which process is load-bearing and which is theatre is most of the skill.

  • Problem resolution

    Issue tracking with a defined path from report to root cause to fix to verification, carried over from the 62304 problem-resolution process on the clinical side.

  • Diagnostics designed for support

    Structured logging on both applications, so a field problem produces evidence instead of a guess.

The point: the commercial software should be maintainable by someone who isn't me. Everything above exists to make that true.

How I work

Say it early, in a form people can act on

When a system's requirements outrun what the platform can actually do, I say so early rather than quietly trying to make it work.

On the gaming-control product, stakeholders had a market vision that hadn't been checked against platform reality — no clear answer on reliably detecting a tap on Android, or on controlling a games console. I brought a MoSCoW breakdown to the people who owned the vision, was explicit about which "musts" weren't achievable in the timeline and why, and proposed concrete alternatives for the rest.

Once we agreed the real scope, the schedule was built with contingency instead of false optimism — and the product reached prerelease without over-promising.

Same instinct, different setting

The Android-versus-PC parity work in case study E is the debugging version of this: name the discrepancy, find the mechanism, don't ship two products that behave differently and hope nobody notices.

About

Instrumentation, broadly defined

The through-line across everything above is finding hidden or ambiguous system state and making it legible.

A biosignal buried in a raw Bayer stream. A hub chip silently hijacking a shared I²C bus mid-provisioning. An RTC fault that read as healthy while holding invalid time. The job is always the same: find the invisible state, prove what it actually is, build something reliable on top of it — then document it so the next person doesn't have to rediscover it.
